# Claims API

Base URL (development): `http://127.0.0.1:8000`
Interactive documentation, generated by FastAPI: `http://127.0.0.1:8000/docs`
OpenAPI schema: `http://127.0.0.1:8000/openapi.json`

**Synthetic data only.** No real customer, policy or claim data.

Phase 1 lodges claims. Phase 2 analyses them. Phase 3 routes them and runs the human review
queue. Governance endpoints (Phase 4) do not exist.

| Method | Path | Phase | Audience | Purpose |
| --- | --- | --- | --- | --- |
| `GET` | `/api/health` | 1 | any | Service health — lets the UI distinguish "backend down" from "form invalid" |
| `POST` | `/api/claims` | 1 | customer | Lodge a storm-damage FNOL |
| `GET` | `/api/claims/{claim_id}` | 1 | customer | Read back a lodged claim |
| `POST` | `/api/claims/{claim_id}/analyze` | 2 | **internal** | Run the claims intelligence workflow |
| `GET` | `/api/claims/{claim_id}/analysis` | 2 | **internal** | Read the stored intelligence result |
| `GET` | `/api/review-queue` | 3 | **internal** | Claims awaiting human review |
| `GET` | `/api/review-queue/{claim_id}` | 3 | **internal** | Everything a reviewer needs for one claim |
| `POST` | `/api/review-queue/{claim_id}/action` | 3 | **internal** | Record a POC review action |

> The Phase 2 and Phase 3 endpoints are **internal, claims-staff endpoints**. They return
> policy interpretation, risk indicators and vulnerability flags, none of which may reach a
> customer. Phase 6 adds the authentication that enforces this; today the separation is
> architectural only.

## POST /api/claims

Creates a claim record and sets its state to **Submitted**.

It does **not** classify, assess, risk-check or route the claim. A `201` means
one thing: the claim exists and has been lodged.

### Request

`Content-Type: application/json`

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `customer.full_name` | string | ✔ | 1–200 chars |
| `customer.email` | string | ✔ | Must look like an email address |
| `customer.phone` | string | ✔ | 6–30 chars |
| `customer.policy_number` | string | ✔ | 4–40 chars |
| `customer.preferred_contact_method` | `email` \| `phone` \| `portal` | | Defaults to `email` |
| `property.loss_address.address_line_1` | string | ✔ | |
| `property.loss_address.suburb` | string | ✔ | |
| `property.loss_address.city` | string | ✔ | |
| `property.loss_address.postcode` | string | ✔ | 3–10 chars |
| `property.property_habitable` | boolean | ✔ | |
| `property.temporary_accommodation_needed` | boolean | ✔ | |
| `damage.date_of_loss` | date `YYYY-MM-DD` | ✔ | Cannot be in the future |
| `damage.time_of_loss` | time `HH:MM:SS` | | Nullable |
| `damage.peril` | `"storm"` | | Phase 1 accepts storm only |
| `damage.incident_description` | string | ✔ | 20–5000 chars |
| `damage.damaged_items` | array | ✔ | 1–25 entries |
| `damage.damaged_items[].area` | string | ✔ | e.g. "Roof" |
| `damage.damaged_items[].item` | string | ✔ | e.g. "Roof tiles" |
| `damage.damaged_items[].description` | string | ✔ | 1–1000 chars |
| `damage.damaged_items[].estimated_value` | number | | Nullable, ≥ 0 |
| `damage.damage_ongoing` | boolean | ✔ | |
| `damage.anyone_injured` | boolean | ✔ | |
| `damage.utilities_affected` | array[string] | ✔ | May be empty |
| `damage.emergency_repairs_done` | boolean | ✔ | |
| `damage.third_party_involved` | boolean | ✔ | |
| `damage.photos_supplied` | boolean | ✔ | |
| `damage.customer_estimated_value` | number | | Nullable, ≥ 0 |

Unknown fields are rejected (`extra="forbid"`) — a typo in a field name fails
loudly instead of being silently dropped.

Field definitions come from `SYNTHETIC_DATA_SPEC.md` §4.2, the Phase 0 definition
of a complete FNOL.

### Response — `201 Created`

```json
{
  "claim_id": "CLM-2026-138004",
  "claim_state": "Submitted",
  "internal_status": null,
  "submitted_at": "2026-09-13T05:57:34.264756+00:00",
  "next_step": "Your claim has been lodged. A claims specialist will review the details you provided and contact you about what happens next.",
  "summary": {
    "policy_number": "POL-HOME-20117",
    "customer_name": "Marama Whitcombe",
    "peril": "storm",
    "date_of_loss": "2026-09-12",
    "loss_address": "18 Kauri Point Road, Titirangi, Auckland 0604",
    "damaged_item_count": 1,
    "customer_estimated_value": 4200.0
  }
}
```

`claim_state` is always `Submitted` on success — never `Assessment`.
`internal_status` is always `null` in Phase 1: nothing has processed the claim.

### Response — `422 Unprocessable Entity`

Returned when the FNOL is incomplete or invalid. Messages are plain language and
safe to render directly to a customer. `fields` is keyed by dotted field path.

```json
{
  "error": "invalid_claim_submission",
  "message": "Some of the claim details need attention before we can lodge your claim.",
  "fields": {
    "customer.email": "This is required.",
    "customer.phone": "This is required.",
    "damage.date_of_loss": "The date of loss cannot be in the future."
  }
}
```

### Response — `503 Service Unavailable`

```json
{
  "error": "claim_creation_failed",
  "message": "We could not lodge your claim just now. Nothing has been submitted -- please try again in a moment.",
  "fields": null
}
```

### Response — `500 Internal Server Error`

```json
{
  "error": "internal_error",
  "message": "Something went wrong at our end. Your claim has not been submitted. Please try again shortly.",
  "fields": null
}
```

**No response ever contains a Python exception, a stack trace or an internal
path.** Detail is logged server-side; the customer gets a stable error code and a
sentence they can act on.

## Validation behaviour

Two layers, deliberately:

1. **Frontend** (`frontend/src/claim/validation.js`) — immediate, friendly
   messages so the customer is not made to submit to find out something is
   missing.
2. **Backend** (Pydantic models + the handler in `app/main.py`) — the
   authoritative check. A browser is not a trust boundary; every submission is
   validated again server-side.

Both layers apply the same rules: required fields, formats, at least one damaged
item, a description of at least 20 characters, no future date of loss.

Everything requiring judgement — completeness against a policy, internal
consistency, plausibility — is the **Validation Agent's** job in Phase 2 and is
deliberately absent here.

## POST /api/claims/{claim_id}/analyze — INTERNAL

Runs the LangGraph claims intelligence workflow over a submitted claim and returns a
structured **recommendation**.

It does **not** change the claim state, contact any customer, or approve, decline or
settle anything. The response says so structurally.

### Request

Optional body:

```json
{ "force_reanalysis": false }
```

A stored analysis is returned if one exists. `force_reanalysis: true` runs the agents again
and stores a new result.

### Response — `200 OK` (abridged)

```json
{
  "claim_id": "CLM-2026-685693",
  "analysis_id": "ANL-9F2A71C40D3B",
  "analysed_at": "2026-09-13T06:14:22.118402+00:00",
  "workflow_version": "phase-2",
  "claim_state": "Submitted",
  "claim_summary": { "policy_number": "POL-HOME-20117", "peril": "storm", "damage_areas": ["Roof"] },
  "agent_results": {
    "intake":     { "agent": "intake", "status": "complete", "findings": [], "recommendation": "...", "confidence": { "value": 0.95, "basis": "..." }, "narrative": "...", "is_recommendation_only": true },
    "policy":     { "...": "..." },
    "validation": { "...": "..." },
    "assessment": { "...": "..." },
    "fraud_risk": { "...": "..." }

  "recommended_next_step": "standard_processing_candidate",
  "recommendation_summary": "Nothing in this analysis argues against ordinary handling...",
  "recommendation_reasons": ["No missing information, inconsistencies or risk indicators found."],
  "overall_confidence": { "value": 0.85, "clears_poc_threshold": true, "threshold_note": "..." },
  "recommended_claim_state": "Assessment",

  "is_recommendation_only": true,
  "action_taken": "none",
  "claim_state_changed": false,
  "boundary_note": "This is analysis, not a decision...",

  "trace": [{ "agent": "intake", "status": "complete", "duration_ms": 1 }],
  "errors": [],
  "degraded": false,
  "llm_provider": "stub"

```

### `recommended_next_step`

A closed enum. None of its values is an action.

| Value | Meaning |
| --- | --- |
| `information_required` | Ask the customer for something before assessing |
| `manual_review_recommended` | A claims specialist should handle the claim |
| `specialist_review_recommended` | Risk indicators warrant a specialist reviewer |
| `standard_processing_candidate` | Nothing argues against ordinary handling — **not an approval** |

### The recommendation / action boundary

`is_recommendation_only`, `action_taken` and `claim_state_changed` are fixed literals, set by
the workflow itself rather than only by the API schema. Acting on a recommendation is a governed
commitment (CP-09, CP-11) that Phase 2 does not perform.

### Response — `404` / `503`

```json
{ "error": "claim_not_found", "message": "We could not find a claim with that reference.", "fields": null }
```

```json
{
  "error": "claim_analysis_failed",
  "message": "The automated analysis could not be completed for this claim. Nothing about the claim has changed, and it can be reviewed manually.",
  "fields": null
}
```

A failed analysis fails closed: the message states explicitly that nothing changed, so it can
never be read as a result.

### Degraded runs

If an agent fails or a dataset is missing, the workflow still completes with `degraded: true`,
that agent's status as `failed`/`degraded`, an entry in `errors`, and a recommendation that
points at a person. "The risk check crashed" never reads the same as "no risk found".

## Phase 3 — routing and human review — INTERNAL

### What `POST /api/claims/{claim_id}/analyze` now also does

Since Phase 3 the analysis **applies** the routing decision. The response gains:

```json
{
  "routing": {
    "outcome": "HUMAN_REVIEW_REQUIRED",
    "priority": "urgent",
    "review_type": "priority_review",
    "primary_reason_code": "E-11_EMERGENCY",
    "reasons": [
      {
        "code": "E-04_ABOVE_AUTOMATED_AUTHORITY",
        "label": "Above automated authority limit",
        "detail": "The estimated value is above the limit the POC rules allow automated handling for.",
        "basis": "business_rule",
        "priority": "high",
        "outcome": "HUMAN_REVIEW_REQUIRED",
        "rule_reference": "docs/DECISION_TABLE.md D-08 · Invariant INV-02 in Phase 4",
        "observed_value": "NZD 42,000",
        "threshold_value": "NZD 20,000",
        "assumption": "POC-proposed threshold pending business approval",
        "source_agent": "assessment"
      }
    ],
    "explanation": ["Above automated authority limit: … Observed: … Compared against: … Source: …"],
    "summary": "Human review required — emergency situation. 4 escalation reason(s) recorded.",
    "recommended_claim_state": "Human Review",
    "rules_evaluated": 12,
    "is_recommendation_only": true,
    "decision_authority": "business_rules",
    "boundary_note": "A routing decision, not a claim decision…"
  },
  "claim_state": "Human Review",
  "claim_state_changed": true,
  "routing_applied": true
}
```

`outcome` is one of `AUTOMATED_PATH_RECOMMENDED`, `HUMAN_REVIEW_REQUIRED`,
`INFORMATION_REQUIRED`. The rule catalogue is in `ROUTING_MODEL.md`.

**Routing can only move a claim to a state where a person or the customer holds it.**
It can never reach Approved/Completed.

```json
  "urgent_count": 1,
  "entries": [
    {
      "queue_id": "RQ-AAAA111122",
      "claim_id": "CLM-2026-889212",

      "review_type": "priority_review",

      "primary_reason_label": "Emergency situation",
      "reason_count": 4,
      "customer_name": "Marama Whitcombe",
      "policy_number": "POL-HOME-20117",
      "estimated_claim_value": 42000,
      "complexity_band": "high",
      "risk_level": "high",
      "confidence": 0.72,

      "assigned_to": null
    }
  ]
}
```

Ordered **urgent → high → standard, oldest first within a band**, in the API rather than
the UI: a queue that buries the emergency claim is worse than no queue.

### GET /api/review-queue/{claim_id}

Returns `claim_id`, `claim_state`, `internal_status`, the full `queue_entry` (reasons,
explanation, `vulnerable_customer`, `emergency`, action `history`), `customer_report` (the
FNOL), `intelligence` (the full analysis), `available_actions`, and
`decision_authority_note`.

`404 claim_not_found` for an unknown claim.

### POST /api/review-queue/{claim_id}/action

```json
{
  "action": "refer_to_specialist",
  "reviewer": "A. Reviewer",
  "notes": "Risk indicators worth a closer look",
  "information_requested": []
}
```

| Action | Effect |
| --- | --- |
| `start_review` | Assigns the claim. No claim-state change |
| `request_information` | → Information Required, entry closed |
| `refer_to_specialist` | Stays in Human Review, marked `specialist_referral` |
| `complete_review` | → Approved/Completed |

Response:

```json
{
  "claim_id": "CLM-2026-889212",
  "action": "complete_review",
  "performed_by": "A. Reviewer",
  "performed_at": "2026-09-13T10:00:00+00:00",
  "previous_claim_state": "Human Review",
  "claim_state": "Approved/Completed",
  "queue_status": "closed",
  "decision_source": "human",
  "poc_note": "A POC review outcome… It does not approve a claim for payment, set a reserve, settle anything, or notify the customer."
}
```

`decision_source` is the fixed literal `"human"` — a review outcome is never attributed to
the model. `complete_review` is POC bookkeeping, and the response says so.

- `404 review_entry_not_found` — the claim is not in the queue.
- `409 invalid_review_action` — the action is not available for the claim's current state.
  Refused, never forced.

## Governance (Phase 4) — internal

Full design in `GOVERNANCE_ENFORCEMENT.md`. Every endpoint below is **GET only**:
nothing under `/api/governance` changes governance state. Lifting a terminal
state is a review action taken by a named person, and lives on the review router
where it is recorded as a human decision — not as a dashboard button.

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/api/governance` | the dashboard — configuration, counts, integrity, audit, suspended claims, denied actions, recent ledger entries |
| GET | `/api/governance/configuration` | the active specification: PreNode, Invariants, TerminalState, derived assurance, thresholds |
| GET | `/api/governance/ledger?limit=` | VerbaLedger entries, newest first |
| GET | `/api/governance/ledger/{claim_id}` | one claim's governance trail, oldest first, in causal order |
| GET | `/api/governance/audit?max_monitor_gap_seconds=` | ledger integrity plus the five audit checks |
| POST | `/api/review-queue/{claim_id}/re-enable-automation` | lift a TerminalState — the only exit |

### What `/api/claims/{id}/analyze` now returns

The analysis response carries a `governance` object at the top level:

```json
{
  "governance": {
    "action": "proceed",
    "permitted": true,
    "decision_id": "…",
    "specification": "home-storm-claims-automation v0.4.0-poc",
    "pre_node": "automation-confidence",
    "pre_node_denied": false,
    "invariant_violated": null,
    "terminal_state": null,
    "fallback": null,
    "assurance_level": "LOW",
    "gamma_threshold": 1.1,
    "confidence": 0.9,
    "confidence_floor": 0.8148,
    "ledger_entry_ids": ["…"],
    "side_effect_performed": true,
    "automation_suspended": false
  }
}
```

`action` is one of `proceed`, `human_queue` (PreNode denied — routed to a person)
or `suspended` (Invariant violated — automation halted). `assurance_level` is
**LOW**, derived by VSL from the F1/F2 facts rather than asserted: output-layer
control blocks a bad action, it does not change how the model decides.

`is_recommendation_only` is still `true` and `action_taken` is still `"none"`.
Governance decides whether an automated *step* may proceed; it never decides a
claim.

### Re-enablement

```
POST /api/review-queue/{claim_id}/re-enable-automation
{
  "authorised_by": "A. Reviewer",
  "root_cause_analysis": "…",              // ≥ 20 chars, required
  "specification_update_proposal": "…"     // ≥ 20 chars, required
}
```

- `409 invalid_review_action` — automation is not suspended for this claim.
- `422` — the evidence is missing or too thin. The framework refuses an empty
  root-cause analysis at construction; the schema refuses a token one earlier.

Success returns the `human_authorised_transition_id`, the successor instance and
`decision_source: "human"`. **It does not change the claim's state.** The reviewer
still holds it; only future automated steps become permitted again.

### Audit CLI

```
python -m governance.audit_cli verify | audit | certify | conformance | summary
```

Exit `0` passed, `1` failed, `2` could not run. An open terminal state fails the
audit by design and exits 1.
